# AI 와인 추천 — "이상형 월드컵" 브라켓 추천 설계

## 배경

지금까지의 결과화면은 3단계 인트로(자리/가격대/타입) 후 카드 2장 + 다이얼(가격 UP/DOWN,
지역 변경, 페어링 검색)로 계속 재조회하는 구조였다. 이 방식의 문제:

1. 첫 추천이 항상 `country_index=0, region_index=0`(SKU 개수 최다 지역)으로 고정돼
   지역이 다양하게 안 보임.
2. 카드 A/B가 `countryIndex`/`regionIndex` state를 공유해서 항상 같은 지역 와인만 보여줌.

사용자 제안으로, 지역 고정/카드 중복 문제를 다이얼 미세조정이 아니라 **"이상형 월드컵" 형태의
토너먼트 브라켓**으로 재설계하기로 함 — 매 라운드 서로 다른 축(산도/아로마/스토리/철학)으로
대비되는 두 와인 중 하나를 사용자가 직접 골라 8강→준결승→결승으로 좁혀가는 방식. Gemini API를
이 과정의 후보 선정(아로마 분류는 실데이터로 대체됨)과 콘텐츠 생성(3·4경기)에 활용한다.

## 목표

- 기존 결과화면(다이얼+카드 2장)을 브라켓 UI로 완전히 대체한다.
- 각 라운드는 실제 데이터에 근거한 대비를 보여준다 — 허위/날조 콘텐츠(특히 실존 인물 언급)를
  만들지 않는다.
- 최종적으로 와인 1병이 "이거야" 최종 추천으로 나온다.

## 비목표

- 다이얼 방식(가격 UP/DOWN 개별 조정) 유지 — 가격/지역 버튼은 브라켓을 "새로 시작"하는
  리셋 트리거로 의미가 바뀐다.
- 계정별 취향 학습/히스토리 — 이번 스코프 밖.

## 전체 흐름

1. 기존 3단계 인트로(자리/가격/타입) 그대로.
2. 인트로 완료 즉시 `GET /api/bracket` 한 번 호출, 로딩 문구("추천 찾는 중...") 표시.
   백엔드가 8강 대진표(후보 8명 + 4경기 매치업) 전부를 이 한 번의 응답에 담아 내려준다.
3. 8강(4경기) → 준결승(2경기) → 결승(1경기). 매 라운드 카드 2장 중 하나 클릭 = 승자 선택,
   다음 라운드로 진행. **이 구간은 이미 받은 데이터만으로 진행 — 추가 API 호출 없음.**
4. 결승 승자 1병 = 최종 추천 카드(기존 종합 카드 포맷: 사진+이름+가격+노트+persona).
5. 가격대/지역 변경, 페어링(음식) 변경 → 파라미터 바꿔서 `/api/bracket` 재호출, 브라켓 처음부터
   다시 시작.
6. 페어링은 8강 후보를 뽑는 단계부터 반영한다(그 음식과 taste 궁합이 좋은 후보 위주로 8명 구성) —
   기존 `score_by_pairing`을 후보 풀 선별에 재사용.

## 8강 매치업 구성 — 4경기

각 경기는 특정 축으로 뚜렷이 대비되는 두 후보를 보여준다. 후보 풀은 기존
`query_candidates`(타입+가격+지역 필터, region_cache 폴백 포함)로 가져온 뒤 wishes/reviews
상위 20~30개로 추리고, 그 안에서 아래 로직으로 8명(경기당 2명, 브랜드 중복 없이)을 뽑는다.

| 경기 | 축 | 데이터 소스 | 선정 로직 |
|---|---|---|---|
| 1경기 | 산도 높음 vs 낮음 | `wine_notes.taste`(JSON, 이미 파싱 중) | 후보 풀에서 acidity 최댓값/최솟값 하나씩 |
| 2경기 | 과일향 위주 vs 꽃·2,3차향 위주 | `pos.tb_pdata.aroma`(영어 태그 배열, 32,613건 전수 확인) — `pdata_id`로 조인 | 고정 키워드 매핑(과일류 vs 꽃/오크/가죽/향신료류)으로 분류 후 각 그룹에서 하나씩. Gemini 불필요 |
| 3경기 | 실존 인물·행사 언급 실화 A vs B | `wine_article_brands`(article_id↔brand_name, 2,930건)로 후보 브랜드의 실제 기사 매칭 → Gemini가 그 기사 안에 검증 가능한 인물/행사 언급(정상 만찬, 시상식 등)이 있는지 판별하고 있으면 한 줄 요약 + 기사 URL을 출처로 반환 | Gemini 1회 호출(후보 여러 개 배치) |
| 4경기 | 생산자 철학 문구 A vs B | `brand_intro.introText`(1,131개 브랜드 소개글) | Gemini가 소개글을 1~2문장 "철학 문구" 톤으로 요약 |

**중복 방지**: 8명은 서로 다른 item_cd이자 가능하면 서로 다른 브랜드로 뽑는다(같은 브랜드가
여러 경기에 나오는 건 허용하되, 같은 경기 내 두 후보는 항상 다른 브랜드).

**3경기 폴백**: 후보 풀 안에 `wine_article_brands` 매칭이 있는 브랜드가 2개 미만이면, 이 경기는
일반 후보 두 개(브랜드만 다름)로 대체하고 유명인 문구 없이 기본 소개만 보여준다.

## 후보 부족 시 처리

타입+가격대+지역 조합이 좁아서 서로 다른 8개를 못 채우면, **지역 범위를 자동 확장**한다 —
같은 타입 내 다른 지역까지 순차로 포함시켜(region_cache의 타입별 순서 재사용) 8개가 채워질
때까지 넓힌다. 화면상 지역 표시는 사용자가 고른 지역을 유지하되, 실제로는 인접 지역 와인이
섞여 있을 수 있다.

## 기술 구조

### API

`GET /api/bracket`
파라미터: `price_tier`, `country_index`, `region_index`, `wine_type`, `pairing_text`(선택) —
기존 `/api/recommend`와 동일한 파라미터 세트.

응답 형태(초안): 각 카드는 기존 `WineCard` 필드 전부 + `axis_label`(그 경기 축에서 이 와인이
어떤 값인지 — 1경기는 "산도 4/5" 같은 텍스트, 2경기는 아로마 태그 리스트, 3경기는 인용구+기사
URL, 4경기는 철학 문구 텍스트)을 갖는다.
```json
{
  "matches": [
    { "round": "quarterfinal", "axis": "acidity", "cards": [ <WineCard & {axis_label}>, <WineCard & {axis_label}> ] },
    { "round": "quarterfinal", "axis": "aroma", "cards": [...] },
    { "round": "quarterfinal", "axis": "story", "cards": [...] },
    { "round": "quarterfinal", "axis": "philosophy", "cards": [...] }
  ]
}
```
준결승/결승 매치업은 프론트가 8강 승자들로 로컬 구성한다(추가 필드 불필요 — 카드 자체가
기존 종합 카드 정보를 다 갖고 있으므로).

### 백엔드 파이프라인 (`/api/bracket` 핸들러)

1. 기존 `find_with_fallback` + `query_candidates`로 후보 풀 조회(지역 자동 확장 포함).
2. `pairing_text` 있으면 `score_by_pairing`으로 정렬 후 상위 20~30개로 추림.
3. 1경기(산도), 2경기(아로마 태그): 로컬 정렬/분류로 즉시 확정.
4. 3경기, 4경기: Gemini 호출 2건을 **동시에**(`asyncio.gather` 또는 병렬 요청) 날려서 응답 지연 최소화.
5. 8명 확정 후 `matches` 배열로 응답.

### 프론트 상태

- 인트로 완료 시 `/api/bracket` 호출, 응답을 `bracket` state에 저장.
- `currentRound`(quarterfinal/semifinal/final), `currentMatchIndex`, `winners` 배열로 진행
  상태 관리. 카드 클릭 시 승자를 `winners`에 push하고 다음 매치로 이동 — 8강 끝나면 승자 4명으로
  준결승 매치 2개를 로컬 구성, 준결승 끝나면 결승 매치 1개 구성.
- 가격/지역/페어링 버튼 클릭 시 브라켓 전체 상태 리셋 + `/api/bracket` 재호출.

### 카드 표시

- 8강 각 경기: 그 경기 축에 해당하는 정보를 카드에 강조 표시(1경기=산도 dot, 2경기=아로마 태그
  칩, 3경기=인용구+기사 출처 링크, 4경기=철학 문구) — 기존 종합 카드보다 축약된 포맷.
- 준결승/결승: 기존 종합 카드(사진+이름+가격+노트+persona) 그대로.

## 테스트 고려사항

- 아로마 키워드 매핑 함수: 순수 함수, 유닛테스트 가능(예: `["Blackcurrant","Vanilla"]` →
  fruit-leaning 판정).
- 8강 후보 선정 로직(중복 방지, 폴백): Gemini 호출부는 mock, 선정 로직 자체는 유닛테스트.
- 기존 `/api/recommend`는 그대로 유지(호환성 — 필요 없어지면 별도 후속 정리).
